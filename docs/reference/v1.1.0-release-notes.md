# MiniContainer v1.1.0

v1.1.0は複数imageの構築・foreground実行と、標準kernelのtask-local fault分離を提供するminor releaseである。
標準MiniOS kernelを`086f2e3fa54f751cd28c5fcd2bed205830bd2934`へ固定する。

## 互換性と更新時の注意

既存のmanifest v1 bundle、stdin/EOF、stdout/stderr、guest終了code、detachedのid・ps・stopを維持する。
boot/Ready wire ABI 1.2、ABI依存`minios-abi-v0.2.0`、bundle digest算式、instance state、OCI media typeは変更しない。
古いminorのbundleはimport/exportでbytesを保持し、kernel更新だけのためにimageを再buildする必要はない。

**manifest v2の異常終了には観測可能な変更がある。** 旧kernelでは不正命令や未写像storeがVM全体のGuestErrorとなり、CLIはhost error125を返した。
新kernelでは当該taskを終了code70で回収し、他taskを継続する。CLIはPID順で最初の非zero結果を終了codeにする。
v1のfatal faultとkernel・control・cleanupの障害は従来どおりhost error125である。
公開済みv1.0.0はmanifest v2/ProcExit実行を保証対象外としており、その既存v1公開契約を変更するreleaseではない。

利用者が保存したkernelファイルは自動更新されない。新archiveの`kernel/minios.bin`を`--kernel`へ渡すか、sourceから同じ固定SHAをビルドする。
v1.0.0のCLIは複数taskを受理しないため、新kernelだけを古いCLIへ組み合わせてv2を実行できるとは扱わない。

## 追加した操作

- `minictr image build-multi TAG --image NAME ELF ...`で1〜4 imageを入力順に登録する。`--arg`は直前imageへ渡す。
- manifest v2を通常のforeground `run`で実行し、PID別終了結果をstderrへ表示する。結果の到着順は任意である。
- stdout/stderrは全taskの共有streamで、task別の出力には分離しない。stdinも共有経路であり、task別配送を保証しない。
- `cargo xtask compat --minios-rev <SHA> --multi`で標準pinとは独立に新しいMiniOSを検証できる。

CLIとkernelのビルドから正常2task・fault＋survivorまでの手順は
[複数taskサンプル](https://github.com/kunihiko-t/minicontainer/blob/v1.1.0/examples/multi-task/README.md)を参照する。
通常のv1手順は[README](https://github.com/kunihiko-t/minicontainer/blob/v1.1.0/README.md)を参照する。

## 修正と検証

短命guestがREADYを書いてQEMUが正常終了した場合、detached起動で未読READYを失わず起動成功を確認する。
READYのない終了、QEMUの異常終了、timeout、signal、失敗時の回収は維持する。

検査はRust1.98.0とlockfileを使い、Ubuntuの実QEMUでv1 hello/echo、stdin/EOF、exit42、fault、timeout/signal、detached/stale/stop、process・payload回収を確認する。
複数taskの正常実行とillegal/store fault分離、旧ABI bundle、配布archive、OCI相互運用も確認する。
macOS CIはhost検査を行う。物理FPGAとmacOS実機QEMUは未確認である。

## 維持する制約

manifest v2の`--detach`は起動前に拒否する。task別I/O、Docker/Linux application ABI互換は提供しない。
kernelの追加syscallを使うguestは対応kernel revisionを明示する必要があり、ABI versionだけで機能の存在を判断しない。
配布kernelのcode量は増えているが、必要なQEMU下限8.2.0、memory既定128 MiB、vCPU既定1は変更しない。
MiniContainerは学習用ランタイムであり、本番向けマルチテナント分離の保証ではない。
